# 云南自然灾害应急协同决策平台 — 前端说明文档

> 本文档面向后端开发同学，说明前端已实现的功能、所需API接口、数据结构及对接要点。

---

## 一、技术栈与启动

| 项目 | 说明 |
|------|------|
| 框架 | Vue 3 + TypeScript + Vite |
| UI库 | Element Plus |
| 状态管理 | Pinia |
| 图表 | ECharts |
| HTTP客户端 | Axios（普通请求）+ 原生 fetch（SSE流式） |
| 前端端口 | 3000（dev） |
| 后端代理 | Vite 将 `/api` 代理至 `localhost:8080` |

```bash
cd frontend
npm install
npm run dev
```

开发模式下，前端通过 `src/mock/index.ts` 模拟全部后端API，无需后端即可独立运行。

---

## 二、通用约定

| 项目 | 说明 |
|------|------|
| baseURL | `/api`（Vite代理，生产环境需Nginx反向代理） |
| 认证方式 | `Authorization: Bearer <token>` |
| 响应格式 | `{ code: number, message: string, data: T, timestamp: string }` |
| 成功码 | `code === 0`，前端Axios拦截器自动解包为 `data` |
| 401处理 | 自动跳转登录页，清除Token |
| Token存储 | sessionStorage（刷新页面不丢失，关闭标签页自动清除） |
| 用户信息持久化 | sessionStorage（key: `auth_user_info`），刷新页面不丢失 |
| 日期时间格式 | `"2026-07-24 10:41:37"`（无毫秒、无Z、T替换为空格） |

## 三、角色与权限

前端定义4种角色，路由守卫根据角色控制页面访问：

| 角色值 | 中文名 | 可访问页面 |
|--------|--------|-----------|
| `ADMIN` | 系统管理员 | 首页、事件列表、事件详情、资源调度、知识库管理、Agent与审计、成员管理、大屏展示 |
| `OPERATOR` | 应急指挥人员 | 首页、事件列表、事件详情、AI方案生成、大屏展示 |
| `RESOURCE_MANAGER` | 资源管理员 | 首页、事件列表、事件详情、资源调度、资源申请、大屏展示 |
| `VIEWER` | 普通信息员 | 首页、事件列表、事件详情、灾情上报、角色申请、大屏展示 |

> **注册默认角色**：新注册用户默认为 `VIEWER`（普通信息员），可通过"申请其他角色"功能申请更高权限角色。

## 四、完整API列表

### 4.1 登录认证

| 方法 | 路径 | 请求体 | 响应 data |
|------|------|--------|-----------|
| POST | `/api/auth/login` | `{ username, password }` | `LoginResult` |
| POST | `/api/auth/register` | `{ username, password, realName? }` | `UserInfo` |

**LoginResult 结构：**
```typescript
{
  token: string
  tokenType: string
  expiresIn: number
  userId: number
  username: string
  realName: string
  roleName: 'ADMIN' | 'OPERATOR' | 'RESOURCE_MANAGER' | 'VIEWER'
}
```

> **重要**：登录响应必须包含 `userId` 字段，前端用于关联角色申请等业务。注册成功后不自动登录，需用户手动登录。注册默认角色为 `VIEWER`。

### 4.2 灾情管理

| 方法 | 路径 | 参数 | 响应 data |
|------|------|------|-----------|
| GET | `/api/incident/list` | `?page&size&disasterType?&incidentLevel?&status?&keyword?` | `{ total, list }` |
| GET | `/api/incident/detail` | `?incidentId` | `Incident` |
| POST | `/api/incident/report` | `multipart/form-data` | `{ incidentId, imageUrls }` |

**Incident 结构（核心）：**
```typescript
{
  id: number
  incidentId: string
  incidentName: string
  disasterType: 'earthquake' | 'mudslide' | 'flood' | 'drought' | 'landslide' | 'fire' | 'other'
  incidentLevel: 'I' | 'II' | 'III' | 'IV'
  occurTime: string | null
  location: string | null
  description: string | null
  status: 'processing' | 'completed'
  imageUrls: string | null          // JSON字符串，解析后为string[]
  reporterId: number | null
  reportTime: string | null
  deathCount: number | null
  propertyLoss: number | null
  disposalPlanStatus: 'draft' | 'submitted' | 'accepted' | 'rejected' | null
  resourceDispatchStatus: 'executing' | 'shortage' | 'completed' | null
  createdAt: string
  updatedAt: string
}
```

> **重要**：`imageUrls` 字段是JSON字符串（如 `'["url1","url2"]'`），前端通过 `JSON.parse()` 解析。`disposalPlanStatus` 和 `resourceDispatchStatus` 为null时前端显示"--"。

**灾情上报（POST）请求格式：** `multipart/form-data`
- 普通字段：`incidentName`, `disasterType`, `incidentLevel`, `occurTime`, `location`, `description`, `deathCount`, `propertyLoss`
- 图片字段：`images`（多文件，最多5张，支持 jpg/png/gif/webp，单张≤10MB）

### 4.3 AI方案生成（SSE流式）

| 方法 | 路径 | 参数 | 响应 |
|------|------|------|------|
| GET | `/api/plan/list` | `?incidentId` | `Plan[]` |
| GET | `/api/plan/detail` | `?planId` | `Plan` |
| GET | `/api/plan/stream` | `?incidentId` | SSE文本流 |

**Plan 结构：**
```typescript
{
  id: number
  planId: string
  incidentId: string
  planTitle: string
  planContent: string
  generateTime: string
  status: 'draft' | 'approved' | 'rejected' | 'submitted'
  createdAt: string
  updatedAt: string
}
```

> **SSE流式生成**：前端通过原生 `fetch` + `ReadableStream` 消费SSE流，URL为 `GET /api/plan/stream?incidentId=xxx`。后端需返回 `text/event-stream` 格式，每条消息为纯文本片段（无需`data:`前缀），前端逐字拼接展示。

### 4.4 处置方案管理

| 方法 | 路径 | 请求体 | 响应 data |
|------|------|--------|-----------|
| GET | `/api/disposal-plan/list` | `?incidentId` | `DisposalPlan[]` |
| POST | `/api/disposal-plan/submit` | `{ id, planContent?, incidentId?, submittedBy? }` | `DisposalPlan` |
| POST | `/api/disposal-plan/save-draft` | `{ id, planContent, incidentId? }` | `DisposalPlan` |
| POST | `/api/disposal-plan/reject` | `{ id, rejectReason, incidentId? }` | `DisposalPlan` |

**DisposalPlan 结构：**
```typescript
{
  id: number
  disposalPlanId: string
  incidentId: string
  planContent: string | null
  status: 'draft' | 'submitted' | 'accepted' | 'rejected'
  submittedBy: number | null
  submittedAt: string | null
  rejectReason: string | null
  createdAt: string
  updatedAt: string
}
```

> **后端需实现的联动逻辑**：
> - `POST /disposal-plan/reject`：驳回处置方案后，需同步更新关联灾情的 `disposalPlanStatus='rejected'` 和 `resourceDispatchStatus='shortage'`
> - `POST /disposal-plan/submit`：提交处置方案后，需同步更新关联灾情的 `disposalPlanStatus='submitted'`
> - `POST /disposal-plan/save-draft`：保存草稿后，需同步更新关联灾情的 `disposalPlanStatus='draft'`

### 4.7 角色申请管理

| 方法 | 路径 | 请求体 | 响应 data |
|------|------|--------|-----------|
| POST | `/api/role-application/submit` | `{ targetRole, reason, userId? }` | `RoleApplication` |
| GET | `/api/role-application/list` | `?userId?&status?` | `RoleApplication[]` |
| POST | `/api/role-application/review` | `{ id, approved: boolean, reason?, reviewerId? }` | `RoleApplication` |
| POST | `/api/role-application/receive` | `{ id }` | `RoleApplication` |

**RoleApplication 结构：**
```typescript
{
  id: number
  applicationId: string
  userId: number
  username: string
  realName: string | null
  targetRole: 'ADMIN' | 'OPERATOR' | 'RESOURCE_MANAGER'  // 不可申请VIEWER
  reason: string
  status: 'pending' | 'approved' | 'received' | 'rejected'
  reviewerId: number | null
  reviewerName: string | null
  rejectReason: string | null
  reviewedAt: string | null
  receivedAt: string | null
  createdAt: string
  updatedAt: string
}
```

> **角色申请流程（重要）**：
> 1. 用户提交申请 → `status='pending'`
> 2. 管理员审核通过 → `status='approved'`（**此时不立即变更用户角色**）
> 3. 管理员审核驳回 → `status='rejected'`
> 4. 用户点击"接收审批" → `status='received'`（**此时才变更用户角色**）
>
> **后端需实现的联动逻辑**：
> - `POST /role-application/review`（`approved=true`）：仅更新 `status='approved'`，**不修改**用户角色
> - `POST /role-application/receive`：更新 `status='received'` + `receivedAt=当前时间`，**同时变更用户角色**为 `targetRole`
> - `POST /role-application/receive`：仅 `status='approved'` 的申请可接收，其他状态返回错误

## 五、三栏联动状态逻辑

事件列表页面展示三个状态栏，后端返回的Incident数据需满足以下联动约束：

### 5.1 三栏状态值

| 栏位 | 字段 | 可选值 | null时显示 |
|------|------|--------|-----------|
| 状态 | `status` | `processing`（处置中）、`completed`（已结束） | — |
| 处置方案状态 | `disposalPlanStatus` | `draft`（草稿）、`submitted`（已提交）、`accepted`（已接受）、`rejected`（已驳回） | -- |
| 资源调度状态 | `resourceDispatchStatus` | `executing`（调度中）、`shortage`（资源不足）、`completed`（已完成） | -- |

### 5.2 合法组合

| 状态 | 处置方案状态 | 资源调度状态 | 场景说明 |
|------|-------------|-------------|---------|
| processing | null | null | 刚上报，未开始处理 |
| processing | submitted | null | 已提交方案，尚未调度 |
| processing | submitted | executing | 已请求资源，等待系统管理员处理 |
| processing | submitted | shortage | 资源不足 |
| processing | submitted | completed | 资源调度完成 |
| processing | rejected | shortage | 方案被驳回 |
| completed | accepted | completed | 方案已接受，灾情已结束 |

> **约束**：`status=completed` 时 `disposalPlanStatus` 不能为 `draft`/`submitted`/`rejected`，`resourceDispatchStatus` 不能为 `executing`/`shortage`。`disposalPlanStatus=accepted` 时 `resourceDispatchStatus` 不能为 `shortage`。

## 六、各角色前端功能详情

### 6.1 普通信息员（VIEWER）

- 灾情上报（含图片上传，最多5张）
- 事件列表查看
- 事件详情查看（含现场图片）
- **角色申请**：侧边栏底部"申请其他角色"按钮 → 跳转角色申请页面
  - 提交申请后等待管理员审核
  - 审核通过后，角色申请页面"接收审批"按钮亮起
  - 点击"接收审批"后角色变更，自动跳转登录页重新登录

### 6.2 应急指挥人员（OPERATOR）

- **AI方案生成**（SSE流式）：选择灾情事件后点击"生成"按钮，SSE流式输出方案内容
- **方案编辑**：生成完毕后内容始终可编辑（textarea）
- **保存草稿**：方案详情右下角"保存草稿"按钮，调用 `POST /disposal-plan/save-draft`
- **确认提交**：方案详情右下角"确认提交"按钮，调用 `POST /disposal-plan/submit`，提交给资源管理员
- **拟定处置方案按钮**：仅 `disposalPlanStatus=null` 时显示
- **重新拟定按钮**：仅 `disposalPlanStatus=rejected` 时显示，跳转AI方案生成页面
- **现场图片**：所有状态下均显示，无图片时显示"未上传图片"
- **角色申请**：同VIEWER

### 6.3 资源管理员（RESOURCE_MANAGER）

- **资源调度分配**：仅 `disposalPlanStatus=submitted` 且 `status≠completed` 时显示
- **请求资源**：点击后跳转资源申请页面，支持一次申请多种资源（动态多行），提交后 `resourceDispatchStatus` 变为 `executing`
- **驳回方案**：驳回后 `disposalPlanStatus` 变为 `rejected`，`resourceDispatchStatus` 变为 `shortage`，显示"已驳回方案，等待再次提交"提示
- **现场图片**：所有状态下均显示，无图片时显示"未上传图片"
- **角色申请**：同VIEWER

### 6.4 系统管理员（ADMIN）

- 资源调度页面（含调度指令Tab、资源不足警告处理）
- 知识库管理
- Agent与审计
- **成员管理**（含两个标签页）：
  - 成员列表：查看/搜索/筛选成员，角色变动操作
  - 角色申请：查看所有角色申请，审核通过/驳回操作
    - 审核状态仅显示三种：待审核、已通过、已驳回
    - 已接收（received）状态在管理员视角下显示为"已通过"
    - 操作栏：pending状态显示"通过"和"驳回"按钮，其他状态显示"-"
- **不包含**AI方案生成页面
- **不包含**"申请其他角色"按钮（ADMIN无需申请角色）

## 七、角色申请完整流程

```
用户注册（默认VIEWER）
    ↓
侧边栏底部"申请其他角色"按钮（ADMIN不可见）
    ↓
角色申请页面 → 选择目标角色 + 填写理由 → 提交
    ↓ status='pending'
ADMIN在成员管理"角色申请"标签页审核
    ↓
    ├─ 审核通过 → status='approved'（不立即变更角色）
    │     ↓
    │   用户侧边栏"申请其他角色"按钮出现红点提示
    │     ↓
    │   用户点击"接收审批" → status='received' + 角色变更
    │     ↓
    │   自动跳转登录页 → 重新登录后角色已变更
    │
    └─ 审核驳回 → status='rejected'
          ↓
        用户在角色申请页面看到"申请失败"+ 红色图标
```

> **关键约束**：审核通过（approved）时**不立即变更用户角色**，角色变更延迟到用户点击"接收审批"（receive）时才执行。这确保用户知情并主动确认角色变更。

## 十、对接要点

### 后端（Spring Boot）需实现

1. **上述全部API接口**，响应格式严格遵循 `{ code: 0, message: "success", data: T, timestamp: "ISO8601" }`
2. **JWT认证**，Token通过 `Authorization: Bearer <token>` 传递
3. **登录响应**必须包含 `userId` 字段（前端用于关联角色申请等业务）
4. **注册接口**：新注册用户默认角色为 `VIEWER`，返回的用户对象需包含 `roleName: 'VIEWER'`
5. **灾情上报接口**需支持 `multipart/form-data`（图片字段名为 `images`）
6. **SSE流式方案生成**：`GET /api/plan/stream?incidentId=xxx` 返回 `text/event-stream`
7. **处置方案状态联动**：驳回方案时同步更新灾情的 `disposalPlanStatus` 和 `resourceDispatchStatus`
8. **资源申请联动**：提交资源申请时同步更新灾情的 `resourceDispatchStatus='executing'`
9. **角色申请两阶段变更**：
   - 审核通过（`POST /role-application/review` approved=true）时**不修改**用户角色
   - 接收审批（`POST /role-application/receive`）时**才变更**用户角色 + 更新 `receivedAt`
   - 仅 `status='approved'` 的申请可调用 receive，其他状态返回错误
10. **日期时间格式**：所有日期时间字段统一使用 `"2026-07-24 10:41:37"` 格式（无毫秒、无Z后缀、T替换为空格）
11. **CORS配置**：开发环境允许 `http://localhost:3000`

### 前端代理配置

开发环境 Vite 代理（`vite.config.ts`）：
```typescript
proxy: {
  '/api': {
    target: 'http://localhost:8080',
    changeOrigin: true,
  }
}
```

生产环境需 Nginx 将 `/api` 反向代理至 Spring Boot。
