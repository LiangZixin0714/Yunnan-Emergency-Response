# 云南自然灾害应急协同决策平台 - 测试报告

## 1. 测试概述

### 1.1 测试目的

本次测试旨在验证云南自然灾害应急协同决策平台的功能完整性、性能指标和系统稳定性，确保各模块接口正常工作，前后端通信通畅，AI服务能够正确生成应急方案。

### 1.2 测试范围

| 测试模块 | 测试内容 |
|----------|----------|
| 认证模块 | 登录、注册、Token认证 |
| 灾情管理模块 | 灾情上报、列表查询、详情查询、状态流转、地理编码、历史坐标补全 |
| 方案管理模块 | 方案生成、列表查询、详情查询、方案审核 |
| 资源管理模块 | 资源列表、资源锁定、资源释放、调度记录 |
| Dashboard模块 | 概览、趋势分析、分布统计、数据大屏、地图态势展示 |
| AI服务模块 | 健康检查、方案生成（同步/流式）、RAG检索 |
| 地理编码服务 | 高德API调用、本地缓存命中、降级匹配 |

## 5. 发现的Bug和修复情况

### 5.1 已修复的问题

| 问题编号 | 问题描述 | 严重程度 | 修复方案 | 状态 |
|----------|----------|----------|----------|------|
| BUG-001 | 登录接口缺少userId字段 | 🔴严重 | 在LoginResponse中添加userId字段，AuthService中传入user.getId() | ✅已修复 |
| BUG-002 | CORS预检请求被拒绝 | 🔴严重 | 在SecurityConfig中添加OPTIONS请求放行规则 | ✅已修复 |
| BUG-003 | VIEWER角色无法访问Dashboard接口 | 🟡一般 | 在SecurityConfig中为Dashboard接口添加VIEWER角色权限 | ✅已修复 |
| BUG-004 | VIEWER角色无法访问incident/list接口 | 🟡一般 | 在SecurityConfig中为incident/list和incident/detail添加VIEWER角色权限 | ✅已修复 |
| BUG-005 | 前端IncidentStatus枚举与后端不一致 | 🟡一般 | 更新前端enums.ts中的IncidentStatus为四态（PENDING/CONFIRMED/PROCESSING/COMPLETED） | ✅已修复 |
| BUG-006 | AiDecisionServiceRealImpl端口配置错误 | 🟢建议 | 修改端口从8001为8002（该类在dev profile下不激活） | ✅已修复 |
| BUG-007 | 灾情上报未存储经纬度 | 🔴严重 | 在Incident实体中添加latitude/longitude字段，上报时调用地理编码服务获取坐标 | ✅已修复 |
| BUG-008 | 高德API超时无降级方案 | 🟡一般 | 实现本地城市坐标缓存 + 模糊匹配降级方案 | ✅已修复 |
| BUG-009 | 历史灾情数据无坐标 | 🟡一般 | 新增坐标补全接口，批量补全历史数据的经纬度 | ✅已修复 |
| BUG-010 | 地图无任何灾情标记显示 | 🔴严重 | Incident实体latitude/longitude使用Double映射DECIMAL(10,7)导致JPA精度转换丢失→改为BigDecimal类型；findWithCoordinates查询返回所有有坐标的灾情（不限状态）；前端Mock数据更新返回全状态灾情 | ✅已修复 |
| BUG-011 | Agent执行记录不同步 | 🔴严重 | Python AI服务orchestrator提交审计记录时日期格式含微秒（如2026-07-26T16:46:21.664824），Java后端AgentRunLogRequest只接受yyyy-MM-dd'T'HH:mm:ss格式，导致反序列化失败 | ✅已修复 |
| BUG-012 | Agent记录无引用来源数据 | 🔴严重 | 同上，日期格式问题导致orchestrator审计记录（含引用来源）无法写入数据库；同时PlanService创建的记录不含引用来源 | ✅已修复 |
| BUG-013 | 资源管理员看到错误的"资源申请已提交"提示 | 🟡一般 | 前端在rejectType为resource_rejected时仍显示"已提交资源申请"提示，正确逻辑应只在系统管理员驳回资源调度时显示 | ✅已修复 |
| BUG-014 | 日期时间显示为UTC时区 | 🟡一般 | Docker容器默认使用UTC时区，导致时间显示与北京时间（UTC+8）不一致 | ✅已修复 |
| BUG-015 | Agent记录排序不符合预期 | 🟡一般 | AgentRunService.listRuns按ID升序返回，最新记录不在第一页；需改为按ID降序排列 | ✅已修复 |

## 6. 性能瓶颈分析

### 6.1 主要瓶颈

| 瓶颈 | 原因 | 影响 |
|------|------|------|
| **方案审查重试** | 审查评分始终为7分，触发多次重试（本次5次） | **最大瓶颈，占总耗时约80%** |
| Embedding模型加载 | 首次请求需要从Hugging Face下载模型 | RAG检索耗时占单次流程的36% |
| 方案生成 | 需要处理RAG返回的3条预案上下文和5条资源信息 | 单次耗时约12秒 |
| vLLM推理 | 通过网络访问远程服务 | 网络延迟约0.5-1秒 |
| **资源调度** | MySQL数据库本地查询 | **耗时极短（0.01秒），可忽略** |

### 6.2 优化建议

1. **优化方案审查逻辑**：
   - 当前审查评分7分未通过，但重试多次后仍为7分
   - 建议调整评分标准：评分≥7分时直接通过，减少不必要的重试
   - 或增加审查Agent的指令，明确说明哪些问题需要修改

2. **Embedding模型缓存**：
   - 将模型文件缓存到本地目录
   - 设置`HF_HOME`环境变量指向本地缓存

3. **RAG检索优化**：
   - 使用预加载机制，在服务启动时加载Embedding模型
   - 考虑使用更轻量级的Embedding模型

4. **方案生成优化**：
   - 限制RAG返回的预案数量（当前已限制为3条）
   - 限制单条预案文本长度（当前已限制为250字）

5. **并行执行优化**：
   - 情报分析和RAG检索可以并行执行
   - 并行执行可将端到端耗时从30秒降低到16秒
