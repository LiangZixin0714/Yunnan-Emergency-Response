# 云南自然灾害应急协同决策平台 - 结项文档

## 1. 项目概述

### 1.1 项目基本信息

| 项目 | 内容 |
|------|------|
| 项目名称 | 云南自然灾害应急协同决策平台 |
| 项目类型 | 多智能体驱动的应急响应系统 |
| 技术架构 | 前后端分离 + AI服务 + 向量数据库 |
| 开发周期 | 2026年7月 |
| 项目状态 | ✅ 已完成（含地图态势展示全链路打通） |

### 1.2 项目目标

本项目旨在建设一套面向云南省自然灾害应急响应的协同决策平台，实现：

- **灾情快速上报**：支持图文混合上报，实现灾情信息的快速录入和分发
- **智能方案生成**：基于大语言模型和应急预案知识库（RAG），自动生成应急处置方案
- **资源高效调度**：实现应急资源的统一管理、锁定/释放和智能调度
- **决策可视化**：通过数据大屏展示灾害态势、资源分布和处置进度
- **多角色协同**：支持 VIEWER、OPERATOR、RESOURCE_MANAGER、ADMIN 四种角色协同工作
- **地理编码服务**：灾情上报时根据地址自动调用高德API获取经纬度，支持本地城市坐标缓存和降级匹配
- **地图态势展示**：基于Leaflet在地图上展示灾情点位，支持聚合和筛选
- **历史数据坐标补全**：提供批量补全接口，为历史灾情数据补充经纬度

### 3.2 核心业务流程

#### 3.2.1 灾情上报流程

```
用户(VIEWER) → 前端 → POST /api/incident/report
                         ↓
                    后端(Spring Boot) → 自动地理编码(高德API + 本地缓存 + 降级匹配)
                         ↓
                    上传图片到MinIO
                         ↓
                    MySQL → INSERT INTO incidents (含latitude/longitude)
                         ↓
                    返回 incidentId + imageUrls
```

#### 3.2.2 AI方案生成流程

```
用户(OPERATOR) → 前端 → POST /api/plan/generate
                          ↓
                     后端(Spring Boot) → 查询灾情信息
                          ↓
                     AI服务(FastAPI) → 情报分析Agent → RAG检索Agent
                          ↓                                        ↓
                     方案生成Agent ← 资源调度Agent ← pgvector    MySQL
                          ↓
                     方案审查Agent（最多5次重试）
                          ↓
                     返回 planId + citations
                          ↓
                     后端保存方案到MySQL
```

#### 3.2.3 资源调度流程

```
用户(RESOURCE_MANAGER) → 前端 → POST /api/resource/dispatch
                                    ↓
                               后端 → Redis分布式锁
                                    ↓
                               检查库存 → 更新库存 → 记录调度
                                    ↓
                               释放锁 → 返回结果
```

#### 3.2.4 处置结束流程

```
用户(RESOURCE_MANAGER/ADMIN) → 前端 → 点击"处置结束"按钮
                                        ↓
                                   确认对话框
                                        ↓
                                   POST /api/incident/complete
                                        ↓
                                   后端验证：处置方案已接受
                                        ↓
                                   更新 incident.status = 'completed'
                                   更新 incident.resourceDispatchStatus = 'completed'
                                        ↓
                                   返回已结束的灾情信息
```

## 7. 状态流转体系

### 7.1 灾情状态

```
pending（待确认）──→ confirmed（已确认）──→ processing（处置中）──→ completed（已结束）
    │
    └──→ 保持状态（可在pending/confirmed/processing间流转）
    
说明：
- pending：灾情上报后的初始状态，表示等待确认
- confirmed：灾情已被指挥人员确认
- processing：灾情正在处置中
- completed：处置结束，需满足处置方案已接受 + 资源调度已完成
```

### 7.2 处置方案状态（plans表）

```
submitted（已提交）──→ accepted（已接受）
        │                      │
        │                      └──→ 可调度资源 → 处置结束
        │
        └──→ rejected（已驳回）──→ OPERATOR重新拟定方案
```

### 7.3 资源调度状态（incident字段）

```
idle（空闲）──→ dispatching（调度中）──→ executing（执行中）──→ completed（已完成）
                                                       │
                                                       └──→ shortage（资源不足）
                                                            │
                                                            └──→ RESOURCE_MANAGER重新调度
```

### 7.4 资源申请状态（resource_requests表）

```
pending（待处理）──→ approved（已批准）
        │
        └──→ rejected（已驳回）──→ 显示驳回理由，OPERATOR重新拟定方案
```

### 11.4 Docker部署步骤

#### 方式一：一键脚本启动（推荐）

```bash
cd deploy

# 启动所有服务（含自动环境检查、端口冲突检测）
./start.sh

# 停止所有服务（保留数据）
./stop.sh

# 停止并清除所有数据（含数据库）
./stop.sh --clean
```

`start.sh` 自动完成以下步骤：
1. 环境预检：检查Docker、Docker Compose可用性
2. 基础镜像准备：预拉取maven、python、node基础镜像
3. 端口冲突检测：自动释放已占用端口
4. 目录初始化：创建数据卷目录
5. 基础设施启动：MySQL、PostgreSQL、Redis、MinIO
6. 健康检查：等待基础设施就绪
7. 业务服务启动：后端、AI服务、前端（含自动构建）
8. 启动总结：显示访问地址和默认账号

#### 方式二：手动Docker Compose命令

```bash
cd deploy

# 1. 启动基础设施（数据库、缓存、对象存储）
docker compose up -d mysql postgres redis minio

# 等待基础设施就绪
sleep 15

# 2. 启动业务服务（含构建）
docker compose up -d --build backend ai-service frontend

# 3. 查看服务状态
docker compose ps

# 4. 查看日志
docker compose logs -f [service-name]
```

## 14. 已修复的问题清单

### 14.1 多资源调度问题

- **问题**：提交多个资源调度时失败
- **原因**：后端在第一个资源锁定后立即将灾情标记为 `completed`
- **修复**：改为标记为 `resourceDispatchStatus = 'executing'`，支持多次调度

### 14.2 状态显示不一致

- **问题**：新上报事件显示"pending"，历史方案显示原始状态值
- **修复**：
  - 新事件默认状态改为 `processing`（处置中）
  - 前端状态映射统一，`pending` 映射为"处置中"
  - 方案列表使用处置方案状态映射（DisposalPlanStatus）

### 14.3 资源调度驳回链路

- **问题**：管理员驳回资源调度后，指挥人员看不到驳回理由
- **修复**：
  - 驳回时同步更新 `disposalPlanStatus = 'rejected'`
  - 驳回时同步更新 `resourceDispatchStatus = 'shortage'`
  - OPERATOR可看到驳回理由并重新拟定方案

### 14.4 处置结束功能

- **问题**：资源调度成功后无法结束处置
- **修复**：
  - 新增 `POST /api/incident/complete` 端点
  - 前端新增"处置结束"按钮
  - 验证处置方案已接受，同时设置 `status = 'completed'`

### 14.5 角色权限完善

- **问题**：ADMIN无法驳回方案和结束处置
- **修复**：
  - `canRejectPlan` 增加 ADMIN 角色
  - `canCompleteIncident` 增加 ADMIN 和 RESOURCE_MANAGER

### 14.6 地图标记无显示（BigDecimal映射修复）

- **问题**：前端地图上无任何灾情标记点位
- **根因分析**：
  1. `Incident` 实体中 `latitude`/`longitude` 字段使用 `Double` 类型映射 MySQL `DECIMAL(10,7)` 类型
  2. JPA/Hibernate 对 `Double` → `DECIMAL` 的映射存在精度转换问题，导致坐标值读取为 null
  3. `findActiveIncidents()` 只返回 `processing` 状态的灾情，而大部分历史数据是 `completed` 状态
  4. 前端 Mock 数据中大屏接口只返回 `processing` 状态灾情
- **修复方案**：
  1. 将 `Incident.java` 实体中 `Double latitude/longitude` 改为 `BigDecimal latitude/longitude`
  2. 地理编码服务 `AmapGeocodeService.java` 返回的 `double[]` 通过 `BigDecimal.valueOf()` 转换存储
  3. 新增 `findWithCoordinates()` 查询方法，返回所有有坐标的灾情（不限状态）
  4. 前端 Mock 数据更新：大屏接口返回所有状态灾情，补全 `location`、`disposalPlanStatus`、`resourceDispatchStatus`、`deathCount`、`propertyLoss` 字段

### 14.7 Agent执行记录同步修复

- **问题**：Operator点击方案生成后，ADMIN在Agent执行记录页面看不到最新记录
- **根因分析**：
  1. Python AI服务的orchestrator在工作流完成后会向后端提交审计记录（含引用来源），但日期格式含微秒（如`2026-07-26T16:46:21.664824`）
  2. Java后端的`AgentRunLogRequest`只接受`yyyy-MM-dd'T'HH:mm:ss`格式
  3. 日期格式不匹配导致反序列化失败，审计记录无法写入数据库
  4. PlanService创建的记录不含引用来源，且与orchestrator记录重复
- **修复方案**：
  1. 在`audit_client.py`中添加`_format_time()`函数，将ISO格式日期去掉微秒后再提交
  2. 移除`PlanService.java`中重复的AgentRun日志记录代码，统一由Python orchestrator提交
  3. 在PlanService调用AI服务时增加`incidentId`参数，确保审计记录正确关联到灾情

### 14.8 引用来源数据显示修复

- **问题**：Agent执行记录的引用来源显示"No Data"
- **根因分析**：同14.7，日期格式问题导致含引用来源的orchestrator审计记录无法写入
- **修复方案**：同14.7，修复日期格式后引用来源数据正常显示

### 14.9 资源管理员提示信息修复

- **问题**：应急指挥人员提交驳回后，资源管理员看到错误的"资源申请已提交"提示
- **根因分析**：前端显示逻辑未检查`rejectType`字段，在`resourceDispatchStatus`为`shortage`时无条件显示
- **修复方案**：修改`Detail.vue`中的`canShowResourceRequestTip`计算属性，增加`rejectType !== 'resource_rejected'`条件判断

### 14.10 Docker时区配置修复

- **问题**：Docker容器内时间显示为UTC时区，与北京时间（UTC+8）相差8小时
- **修复方案**：
  1. 在`docker-compose.yml`中为后端容器添加`TZ=Asia/Shanghai`和`JAVA_TOOL_OPTIONS=-Duser.timezone=Asia/Shanghai`环境变量
  2. 为AI服务容器添加`TZ=Asia/Shanghai`环境变量

### 14.11 Agent记录排序修复

- **问题**：Agent执行记录按ID升序排列，最新记录不在第一页
- **修复方案**：在`AgentRunService.listRuns()`方法中添加按ID降序排序（`b.getId().compareTo(a.getId())`）
